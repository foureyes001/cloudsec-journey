what aws manages

========================================================================== ★★ READ REPLICAS vs MULTI-AZ — the most tested confusion here

READ REPLICAS = SCALING READS

ASYNC replication
	-> eventually consistent, reads can be slightly stale

up to 5 (15 for other apps)

can sit same-az / cross-az / cross-region

can be PROMOTED to its own standalone db
	this breaks replication permanently

★ the app must be changed to point reads at the replica endpoint
	it is NOT automatic

⚠ cost
	cross-AZ replica traffic inside one region = free for RDS
	cross-REGION = paid

MULTI-AZ = HIGH AVAILABILITY / DISASTER RECOVERY

SYNC replication to a standby in another az

★ THE STANDBY IS NOT READABLE
	it does nothing at all until failover

★ multi-az is NOT for scaling
	if the question says "improve read performance",
	the answer is a read replica — never multi-az
ZERO downtime

one DNS name, failover is automatic (~60-120s)

failover triggers
	az loss, instance failure, storage failure, network loss

single-az -> multi-az is ZERO DOWNTIME (just modify)...dont have to manually do anything

★ THE TRAP

a read replica CAN be placed in another az, which looks like multi-az

it is not — replication is async, and there is no automatic failover

MULTI-AZ DB CLUSTER — a third, newer thing

1 writer + 2 READABLE standbys across 3 az

semi-sync

use when you want HA and want the standbys to do real work




⚠ added 2022 — older recordings do not mention it exists

========================================================================== RDS PROXY — managed connection pooler

sits between the app and the db, pools and shares connections

★ solves the LAMBDA CONNECTION STORM

	and exhausting the database

★ can ENFORCE IAM auth

========================================================================== AURORA

aws proprietary — mysql AND postgres compatible

perf claim - ~5x mysql, ~3x postgres

STORAGE

★ 6 COPIES ACROSS 3 AZ

★ 4 of 6 needed for WRITES

★ 3 of 6 needed for READS

self healing, peer-to-peer replication

★ auto grows in 10GB increments up to 128 TB
	never pre-provisioned

REPLICAS & FAILOVER

one writer

★ up to 15 read replicas

sub-10ms replica lag

failover typically < 30s (vs 60-120s on RDS multi-az)

★ ENDPOINTS — the aurora-specific trigger

WRITER endpoint
	always points at the current master, follows failover

READER endpoint
	CONNECTION-level load balancing across all replicas
	★ not request-level — one connection sticks to one replica

CUSTOM endpoint
	a named subset of instances
	e.g. send analytics/reporting to the big instances only

BACKTRACK

★ rewinds the cluster IN PLACE to a point in time, using no backup

★ contrast with snapshot restore, which creates a NEW cluster

CLONING

copy-on-write — fast and cheap

use - make a staging copy of prod without duplicating storage

GLOBAL DATABASE

1 primary region + ★ up to 5 secondary read-only regions

replication lag typically < 1s

★ promote a secondary in < 1 min RTO
	-> this is the cross-region DR answer

SERVERLESS v2

autoscales capacity (ACUs) for unpredictable / spiky load

========================================================================== ELASTICACHE

managed in-memory cache — redis / memcached / valkey

sub-millisecond, takes read load off the database

★ SECOND USE CASE, often the actual answer
	makes the app STATELESS by holding SESSION DATA
	outside the instances

★ THE COST — requires heavy application code changes
	the app must decide what to cache and when to invalidate
	if a question offers a "no code change" option,
	elasticache is probably the wrong answer

★★ REDIS vs MEMCACHED — guaranteed table question

REDIS
	multi-az with AUTO FAILOVER
	read replicas
	PERSISTENCE (AOF)
	backup + restore
	sets and sorted sets
	-> pick redis whenever HA / durability / leaderboards appear

MEMCACHED
	pure cache
	SHARDED across nodes (partitioning)
	multi-threaded
	★ NO replication, NO persistence, NO backup
	-> pick memcached only for a plain distributed cache

⚠ VALKEY is now a supported engine (redis fork)
	newer than most recordings

CACHING STRATEGIES

LAZY LOADING / CACHE-ASIDE
	only cache what was actually asked for
	+ only useful data ends up cached
	- a cache MISS costs 3 trips, and data can go stale

WRITE-THROUGH
	write to the cache every time you write to the db
	+ never stale
	- write penalty, and the cache fills with data nobody reads

TTL
	expiry — used alongside both of the above
